📖 THEORY & CONCEPTS

Understanding Deadlock

A comprehensive guide to deadlock in operating systems — what it is, why it happens, and how to handle it.

FUNDAMENTALS

What Is a Deadlock?

A deadlock is a situation where a set of processes are permanently blocked because each process is holding a resource and waiting to acquire a resource held by another process in the set.

⏳

Indefinite Block

No process in the deadlock set ever makes progress. They are permanently stuck, consuming resources without doing any useful work.

🔄

Circular Dependency

P1 waits for P2, P2 waits for P3, P3 waits for P1 — forming a cycle in the resource wait graph. A cycle is a necessary condition.

📉

System Impact

CPU utilization drops to zero for the blocked processes, throughput falls, and users experience unresponsive applications or services.

COFFMAN (1971)

Four Necessary Conditions

All four conditions must hold simultaneously for deadlock to occur. Breaking even one prevents deadlock entirely.

01
🔒
Mutual Exclusion
At least one resource must be held in a non-sharable mode. Only one process can use it at a time; others must wait.
02
✋
Hold & Wait
A process holds at least one resource while waiting to acquire additional resources currently held by other processes.
03
🚫
No Preemption
Resources cannot be forcibly taken away from a process. They are released only voluntarily after the task completes.
04
🔄
Circular Wait
A set {P0,P1,…,Pn} where P0 waits for P1, P1 for P2, …, Pn waits back for P0 — forming a closed circular chain of dependencies.
MODELING

Resource Allocation Graph (RAG)

The RAG is a directed bipartite graph used to represent the state of resource allocation. It's the foundation of deadlock detection.

🔵 Process Nodes (Circles)

Each circle represents a process. A process can request resources and hold resources assigned to it.

🟡 Resource Nodes (Rectangles)

Each rectangle represents a resource type. Dots inside the rectangle indicate the number of instances of that resource.

━━ Request Edge (P→R, dashed)

Directed edge from Process to Resource: the process is requesting (waiting for) that resource to become available.

━━ Assignment Edge (R→P, solid)

Directed edge from Resource to Process: the resource instance has been allocated (assigned) to that process.

Deadlock Detection Rule

For single-instance resources:
A deadlock exists if and only if the RAG contains a cycle.

For multi-instance resources:
A cycle is necessary but not sufficient. Use the full detection algorithm (similar to Banker's safety check).

💡
The Wait-For Graph simplifies detection by eliminating resource nodes — if P1→R→P2, collapse to P1→P2. Then find cycles in the process-only graph.
HANDLING DEADLOCK

Three Main Strategies

🛡️

Prevention

Proactive

Eliminate at least one Coffman condition by design:

  • Request all resources at once (eliminates Hold & Wait)
  • Total ordering of resource types (eliminates Circular Wait)
  • Allow preemption of resources
🏦

Avoidance

Proactive

Keep system in a safe state at all times:

  • Banker's Algorithm for resource requests
  • Requires advance knowledge of max resource needs
  • Grant request only if resulting state is safe
🔧

Detection & Recovery

Reactive

Allow deadlocks, detect, then fix:

  • Periodic RAG cycle detection
  • Recovery: terminate process(es)
  • Recovery: preempt & rollback resources

PSEUDOCODE

Key Algorithms

1. DFS Cycle Detection (Wait-For Graph)

function detectCycles(graph): visited = Set() recStack = Set() for each node in graph: if node not in visited: if dfs(node, visited, recStack): return DEADLOCK_FOUND return NO_DEADLOCK function dfs(v, visited, recStack): visited.add(v) recStack.add(v) for each neighbor in adj[v]: if neighbor not in visited: if dfs(neighbor, ...): return true elif neighbor in recStack: return true // back-edge = cycle! recStack.remove(v) return false

2. Banker's Safety Algorithm

// Inputs: Allocation, Max, Available function isSafeState(): need[i][j] = max[i][j] - alloc[i][j] work = Available[] finish = [false, false, ...] // n processes safeSeq = [] repeat: found = false for i = 0 to n-1: if finish[i] == false: if need[i] <= work: // can this run? work += alloc[i] // release resources finish[i] = true safeSeq.push(i) found = true until not found if all finish[i] == true: return SAFE, safeSeq else: return UNSAFE // deadlock possible

3. Banker's Resource-Request Algorithm

// Request_i from process P_i function requestResources(i, Request): // Step 1: Check claim limits if Request > Need[i]: raise Error("Exceeded maximum claim") // Step 2: Check resource availability if Request > Available: return WAIT // not enough resources now // Step 3: Tentative Allocation Available -= Request Alloc[i] += Request Need[i] -= Request if isSafeState().isSafe: return GRANT_REQUEST // allocate permanently else: // Rollback state; P_i must wait Available += Request Alloc[i] -= Request Need[i] += Request return WAIT_UNSAFE

4. Holt's Graph Reduction Algorithm (General RAG)

// For single & multi-instance resources function reduceRAG(processes, resources): Work = Available[] Finished = [false, false, ...] repeat: reducedAny = false for each P in processes: if not Finished[P]: // Can all pending requests of P be satisfied? if Requests(P) <= Work: Work += Assigned(P) // simulate release Finished[P] = true reducedAny = true until not reducedAny if all Finished[P]: return NO_DEADLOCK else: return DEADLOCK_DETECTED, unreducedProcesses
REAL-WORLD EXAMPLES

Classic Deadlock Scenarios

🍽️

Dining Philosophers

5 philosophers sit at a round table. Each needs two chopsticks to eat. If all grab the left chopstick simultaneously — deadlock. Solution: allow at most 4 philosophers at the table, or use asymmetric rules.

🌉

Bridge Crossing Problem

A one-lane bridge where cars from both sides enter simultaneously. Neither side can proceed — classic mutual blocking. Solution: traffic light (mutex), preemption (one side backs up).

🗄️

Database Transactions

TX-A locks record R1 then requests R2. TX-B locks R2 then requests R1. Both wait forever. Solution: Timeout-based rollback, wound-wait or wait-die protocols.
